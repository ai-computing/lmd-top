## BUG-01 — Prometheus 미도달 시 collect 가 92초 걸려 첫 화면까지 프리즈 · P0

**재현**
```
LMD_PROM=192.0.2.7:9 lmd-top --snapshot     # 블랙홀 IP(RST 없음)
→ real 1m32.6s
```
TUI 경로는 `run_tui()` 가 UI 루프 진입 **전에** `collect(&cfg).await` 를 동기로 기다린다
(`src/main.rs:867`). 즉 Prometheus 가 죽은 클러스터에서 lmd-top 은 92초간 검은 화면이다.
QA 기준 ENV-01("TUI 는 뜨고 경고 표시, 프리즈 없음")과 PERF-03(첫 화면 <5s) 동시 위반.

**근본 원인 3개**
1. **서킷 브레이커 부재** — `collect()` 는 맨 앞에서 `vector(1)` 도달성 프로브를 하고
   `prom_ok=false` 를 기록하지만(`collect.rs:1137`), 그 결과를 **쓰지 않고** 이후 60여 개
   쿼리를 그대로 전부 시도한다.
2. **순차 쿼리 블록** — `vllm` 구조체 구성부(`collect.rs:1284-1338`)의 10개 쿼리가
   `q(...).await` 로 **직렬** 실행된다(다른 블록은 `join!`/`query_all` 로 병렬).
   쿼리당 12초(6s timeout × 2회 시도) → 이 블록만 120초 규모.
3. **timeout 재시도** — BUG-11 참조. 이미 6초 기다린 timeout 을 한 번 더 시도해 대기가 2배.

**올바른 동작** — 도달 불가가 확인되면 그 사이클의 나머지 Prometheus 쿼리는 즉시 스킵하고
경고만 남긴다. 정상 클러스터 tick 은 3s 이내(PERF-01).

**수정**
- `Config.prom` 을 빈 문자열로 대체하는 대신 `prom::mark_down()/is_down()` 프로세스 전역
  서킷 브레이커 도입 — 프로브 실패 시 세팅, 성공 시 해제. `http_get` 이 down 상태면
  네트워크를 건드리지 않고 즉시 `Err("prometheus unreachable (circuit open)")`.
- 프로브 전용 타임아웃 2초(`query_probe`) — 전체 미도달 collect 를 2초대로 단축.
- `vllm` 블록 10개 쿼리를 `query_all` 로 병렬화(정상 경로 tick 시간도 단축).
- `kube.rs` 의 모든 shell-out 을 `tokio::time::timeout` 으로 외곽 봉인(`--request-timeout`
  이 못 잡는 kubectl 자체 hang 대비).

## BUG-02 — 오버레이 열림 중 마우스 스크롤 누수 + Scale 이 엉뚱한 replica 수로 실행 · P0

**재현**
1. `--mode admin` 으로 기동, Models 뷰에서 **실행 중**(replicas 1)인 모델 A 선택 → `Enter` → 액션 메뉴
2. 메뉴가 열린 상태에서 **마우스 휠**로 **정지된**(replicas 0) 모델 B 로 스크롤
3. `Scale` 실행 → 확인 프롬프트가 **"scale A → 1"** (A 를 끄려던 의도와 반대)

**근본 원인 2개**
1. `src/main.rs:966-975` — 마우스 이벤트 처리가 **모든 오버레이 게이트보다 먼저** 있고
   `continue` 로 빠진다. 키 입력에는 `ui::Overlay::top()` 안전망이 있으나 마우스에는 없다(REG-01).
2. `dispatch_action` 의 `Action::Scale`(`main.rs:643`)이 **이름은 고정된 `subject`** 에서
   가져오면서 **target replica 수는 `app.selected_model()`** — 즉 *현재* 선택에서 재계산한다.
   `Action::RouteDelete` 도 subject 대신 `app.selected_route()` 를 읽는다.

**올바른 동작** — 오버레이가 열려 있으면 마우스 이벤트 무시. 액션의 모든 파라미터는
메뉴를 연 시점의 subject 에서 해석.

**수정** — 마우스 분기를 `Overlay::top(&app).is_some()` 로 게이트. `Action::Scale` 은
subject 이름으로 모델을 조회해 target 을 계산(`model_by_name`). `RouteDelete` 는 subject 로 라우트 조회.

## BUG-03 — 액션 메뉴·커맨드 팔레트의 선택행 텍스트가 보이지 않음 · P0

**재현** 실기 터미널에서 액션 메뉴(`Enter`) 또는 커맨드 팔레트(`:`) 를 열면 선택된 행의
라벨이 배경과 같은 색으로 사라진다. 폼(compile/deploy/objective/prefetch)의 선택 필드 라벨도
어두운 회색으로 비선택 행보다 **덜** 읽힌다.

**근본 원인** `C_HL()` 은 하이라이트 **배경**색이다(soft 테마 `Rgb(49,50,68)`, 그 외 `Indexed(238)`).
그런데 3개소에서 **전경**색으로 쓰인다:
- `overlays.rs:448` 액션 메뉴 활성 행 라벨 `fg(C_HL())`
- `overlays.rs:534` 팔레트 활성 행 라벨 `fg(C_HL())`
- `overlays.rs:593` `choice_row()` 활성 필드 라벨 `fg(C_HL())` — 모든 옵션 폼 공통

앞의 두 곳은 같은 행에 `line.style = bg(C_HL())` 도 적용된다(`:477`, `:557`)
→ **fg == bg → 글자가 완전히 사라진다.**

**올바른 동작** 선택 항목이 가장 뚜렷해야 한다.

**수정** 세 곳의 활성 스타일을 `fg(C_ACC()) + BOLD` 로 교체(하이라이트 배경 위에서도 대비 확보).
회귀 테스트: TestBackend 로 메뉴/팔레트를 렌더해 선택 행의 모든 셀에서 `fg != bg` 를 단정.

## BUG-04 — `norm_pct` 가 1% 이하 util 을 100배로 부풀림 · P0

**재현** GPU 가 정확히 1% 로 동작할 때 화면에 **100%** 로 표시. 0.5% → 50%.
```rust
fn norm_pct(v: f64) -> f64 { ... else if v <= 1.0 && v > 0.0 { v * 100.0 } ... }   // collect.rs:1528
```

**근본 원인** "0..1 비율이면 %로 환산" 휴리스틱을 **샘플 하나만 보고** 판정한다. 그러나
세 util 메트릭 모두 원래 0–100 % 스케일임이 실측으로 확인된다:
- `DCGM_FI_DEV_GPU_UTIL` — 7일 max **96** (라이브 확인)
- `furiosa_npu_core_utilization` — furiosa-smi `pe_usage_percentage` 유래(exporter `/metrics` 확인)
- `RBLN_DEVICE_STATUS:UTILIZATION` — rbln-stat util(%) 유래

즉 스케일 추정 자체가 불필요하고, 저사용률 구간에서 100배 오류만 낸다.
util 은 알림 임계(`UTIL_WARN 60` / `UTIL_BAD 85`), 색상, 스파크라인, `--json` 의
`util_avg_pct`, 배치 판정의 "유휴" 계산에 모두 쓰이므로 파급이 넓다.

**수정** `norm_pct` 를 `clamp_pct`(NaN→0, 0..100 클램프, 스케일 변환 없음)로 교체.

## BUG-05 — 형제 변형 모델의 메트릭이 서로 뒤바뀜 · P0

**재현** `x` 와 `x-fp8` 을 동시 서빙하면 `x-fp8` 행에 `x` 의 tps/kv/ttft 가 붙는다.
```rust
// collect.rs:2241
for k in v_run.keys() {                                  // BTreeMap = 알파벳 순
    if dn.contains(&kn) || kn.contains(&dn) { return Some(k.clone()); }   // 첫 부분일치 반환
}
```
`deploy="x-fp8"` → 정규화 `"xfp8"`. 첫 키 `"x"` 가 `dn.contains("x")` 로 걸려 그대로 반환.
**짧은 이름이 항상 이긴다.**

**올바른 동작** 완전일치 우선, 그다음 가장 긴(가장 구체적인) 일치.

**수정** 후보를 모두 모아 `(정확일치, 일치 길이)` 로 최댓값 선택. 회귀 테스트로 `x`/`x-fp8` 고정.

## BUG-06 — 모델 ID 가 YAML·셸에 무이스케이프로 삽입 (무효 매니페스트 + Job 셸 주입) · P0

**재현**
```bash
# (a) 무효 YAML
lmd-top --plan compile --model 'Qwen/Qwen2.5"-0.5B-Instruct' --vendor rbln | yq .
→ while parsing a flow mapping ... expected ',' or '}'
lmd-top --plan compile --model $'Qwen/foo\nbar-llama' --vendor rbln | yq .
→ expected '<document start>'

# (b) 셸 명령 주입
lmd-top --plan compile --model 'Qwen/x; echo PWNED; #' --vendor furiosa
→ command: ["sh","-c","... fxb build Qwen/x; echo PWNED; # /work/out/model -tp 8 ..."]
```

**근본 원인** 생성 매니페스트가 사용자·원격 문자열을 `value: "{model_id}"` 및
`sh -c "... {model_id} ..."` 에 **그대로 보간**한다(`app/compile.rs`, `app/deploy.rs`).

**단순 자해가 아니라 원격 입력원이 있다** — Zoo 뷰의 `r` 키는
`catalog.rs:94 fetch_zoo_live()` 로 `https://huggingface.co/api/models?author=furiosa-ai` 를
curl 해서 응답 JSON 의 `id` 를 **검증 없이** `ZooModel.source` 로 삼는다. 그 값이 그대로
compile Job 의 `sh -c` 라인에 들어간다 → 원격 JSON 이 클러스터 내 Job ServiceAccount 권한으로
임의 명령을 실행시킬 수 있는 경로.

**올바한 동작** 경계에서 거부하고, 통과한 값도 문맥별로 이스케이프.

**수정** 3중 방어:
1. `catalog::valid_model_id()` — HF 모델 ID 문법(`[A-Za-z0-9._-]+(/[A-Za-z0-9._-]+)?`) 검증.
   `fetch_zoo_live` 수집 시 위반 항목 폐기, `--plan`/폼 제출 시 명시적 오류.
2. `yamlq()` — YAML 이중인용 이스케이프(`\`, `"`, 개행/제어문자)를 모든 보간 지점에 적용.
3. `shq()` — POSIX 단일인용 셸 이스케이프를 `sh -c` 보간 지점에 적용.

## BUG-07 — `--plan compile --vendor gpu` 가 벤더 혼합 매니페스트를 만든다 · P1

**재현**
```bash
lmd-top --plan compile --model Qwen/Qwen2.5-0.5B-Instruct --vendor gpu
```
결과물: 경로 `compiled/.../gpu/**rngd**-tp1-pp1-s8192`, ConfigMap 은 **RBLN** `optimum.rbln`
스크립트, Job 이미지는 **`furiosaai/furiosa-llm:latest`**, 주석은 "RBLN: ... LMD_COMPILE_IMAGE_RBLN"
인데 실제 이미지는 Furiosa. 적용하면 반드시 실패하는 쓰레기 Job.

**근본 원인** 컴파일은 NPU(rbln/furiosa) 전용 개념이고 `compat::compilable_vendors()` 도
그 둘만 반환한다. 그런데 `plan_vendor()`(`main.rs:190`)가 `gpu|nvidia` 를 통과시키고,
하위 분기가 모두 2지 선택(`if rbln {..} else {furiosa}` / `if vendor=="furiosa" {..} else {rbln}`)
이라 `gpu` 가 매 분기에서 서로 다른 쪽으로 떨어진다.

**수정** `--plan compile` 은 `--vendor gpu` 를 명확한 오류로 거부
("compile targets NPU only (rbln|furiosa); GPU models are served directly — use --plan deploy").
`--plan deploy --vendor gpu` 는 정상이므로 유지.

## BUG-08 — 존재하지 않는 namespace 에서 경고 없이 빈 뷰 · P1

**재현**
```
LMD_NS=no-such-ns lmd-top --snapshot
→ [models] 0 / [pods] 0 / [routes] 0 ... [warnings] 섹션 자체가 없음
```
`kubectl get deploy -n no-such-ns -o json` 은 **성공 + 빈 items** 를 반환하므로 컬렉터가
오류를 감지할 수 없다(라이브 확인). 사용자는 "이 클러스터엔 모델이 없다"와
"namespace 이름을 잘못 썼다"를 구분할 수 없다.

**수정** `collect_setup()` 이 이미 `ns_exists` 를 프로브한다 — 그 결과를 warnings 로 승격:
`probed && !ns_exists` → `namespace 'X' does not exist — check LMD_NS`.

## BUG-09 — kubectl 부재/실패 시 원시 OS 오류와 이유 없는 경고 · P1

**재현** `PATH` 에서 kubectl 제거 후 `--snapshot`:
```
! kube httproute                                       ← 사유가 아예 없음
! kube deploy: No such file or directory (os error 2)   ← 원인 추론 불가
! kube pods: No such file or directory (os error 2)
! inv nodes: No such file or directory (os error 2)
```

**근본 원인**
- `kube::get_json` 이 `Command::output()` 의 `io::Error` 를 `?` 로 그대로 전파.
- `collect_kube` 의 httproute 분기는 `else { warn.push("kube httproute".into()) }` — 사유 미포함.
- gateway/inferencepool/inferenceobjective/scaledobject 컬렉터는 `if let Ok(v) = ...` 로
  **경고조차 없이** 실패(REG-08 잔존). RBAC 제한 계정에서 빈 뷰와 권한 오류가 구분 안 됨.

**수정** `kube.rs` 에서 `NotFound` io 오류를 `kubectl not found in PATH — install kubectl or fix PATH`
로 치환. 무경고 컬렉터 4개에 사유 포함 경고 추가. httproute 경고에 원인 문자열 부착.

**수정** 누락 4개를 `DEPS` 에 추가(영향 문구 포함). 재발 방지 테스트: `collect.rs` 가
읽는 DCGM 계열 상수가 전부 `DEPS` 에 있는지 단정.

## BUG-11 — Prometheus 재시도가 상태 오류·타임아웃까지 재시도 · P1

## BUG-12 — CJK 이름이 있는 표에서 열이 밀린다 · P1

**재현** 한글 모델명/pod 명이 있는 행에서 그 뒤 열이 오른쪽으로 밀린다.
```rust
format!("{:<20} ", truncw(&n.name, 20))   // ui/mod.rs:4139 외 12개소
```
`truncw` 는 **표시폭**(unicode-width) 기준으로 자르고, `{:<20}` 은 **char 수** 기준으로 채운다.

`{:<N}` + `truncw` 조합 전체를 치환. 회귀 테스트로 CJK/ASCII 모두 `dwidth == n` 단정.

## BUG-13 — chunked 디코딩이 lossy 문자열 위 바이트 오프셋으로 동작 · P1

**재현(코드 경로)** `http_get_once` 는 응답 전체를 `String::from_utf8_lossy` 로 문자열화한 뒤
`dechunk()` 가 **16진 청크 크기를 `&str` 바이트 오프셋으로** 슬라이스한다.
서버가 멀티바이트 문자 중간에서 청크를 끊으면(예: `2\r\n<0xE2 0x82>\r\n1\r\n<0xAC>\r\n0\r\n\r\n`)
그 바이트열은 유효 UTF-8 이 아니므로 `from_utf8_lossy` 가 U+FFFD(3바이트)를 삽입해
**이후 모든 오프셋이 어긋난다**. `get(..size)` 가 `None` 이 되는 순간 `dechunk` 는
남은 전체(청크 헤더·CRLF 포함)를 붙이고 중단 → JSON 파싱 실패 → 해당 뷰가 조용히 빈다.
비ASCII 라벨(한국어 pod/모델명)을 쓰는 클러스터에서 발현 가능(FAULT-04).

기존 테스트 `dechunk_non_ascii_boundary_no_panic` 은 **패닉 없음만** 단정해 이 오류를 통과시킨다.

**수정** 디코딩을 바이트 기준으로 이동: `http_get_once` 가 `Vec<u8>` 를 유지하고
`dechunk_bytes(&[u8]) -> Vec<u8>` 로 청크를 합친 뒤 마지막에 한 번만 UTF-8 변환.
회귀 테스트: 경계가 쪼개진 멀티바이트 문자가 **정확히 복원**되는지 단정.

## BUG-17 — `--plan deploy --model X` 가 요청하지 않은 다른 모델의 매니페스트를 만든다 · P0

**재현** (라이브 클러스터, 무엇을 넣어도 결과가 같다)
```
$ lmd-top --plan deploy --model Qwen/Qwen2.5-0.5B-Instruct --vendor rbln   | grep 'name: serve-'
metadata: { name: serve-v4flash, ... }          ← 요청한 모델이 아니다
$ lmd-top --plan deploy --model meta-llama/Llama-3.1-8B-Instruct --vendor gpu | grep 'name: serve-'
metadata: { name: serve-v4flash, ... }          ← 역시
```
9가지 (모델 × 벤더) 조합 전부 `serve-v4flash` — 클러스터에 있던 무관한 아티팩트. `--model` 이
사실상 무시된다. 이 매니페스트를 `--apply` 하면 **의도한 모델이 아닌 다른 모델의 Deployment·
Service·InferencePool·HTTPRoute** 가 생성/변경된다.

**근본 원인** `plan_deploy_for_model`(`app/compile/plan.rs`)이 합성 아티팩트를 `snap.artifacts`
뒤에 push 하고, 대상을 **선택 상태로 전달**한다:
```rust
app.snap.artifacts.push(a);
app.selected = old_len;      // raw 인덱스
app.open_deploy_form();      // 내부에서 selected_artifact() → sel_orig() = order()[selected]
```
`app.selected` 는 **표시 순서(display order)** 인덱스이고 `order()` 는 Serving 뷰의 정렬·그룹핑
결과다. raw push 인덱스를 그대로 넣으면 `order()[old_len]` 이 전혀 다른 아티팩트를 가리킨다.
(HEAD 의 `app/compile.rs` 에도 동일 코드 — 오늘 리팩터가 만든 문제가 아니라 기존 결함이다.)

이 결함이 BUG-06 검증을 가리기도 했다: 주입 문자열이 "거부"된 게 아니라 **모델 자체가 다른 것으로
대체**돼 매니페스트가 만들어진 것이었다.

**수정**
- raw 인덱스를 표시 위치로 변환: `app.selected = app.order().iter().position(|&i| i == old_len)`.
- 심층 방어: 폼이 요청한 모델에 안 걸렸으면 YAML 을 내지 않고 명시적 오류로 실패
  (`deploy plan resolved to 'Y' instead of 'X' — refusing to emit a manifest for the wrong model`).
- 회귀 테스트는 **구조가 아니라 정체성**을 단정한다(정렬을 뒤흔드는 아티팩트 3개를 심어 두고
  생성물이 요청 모델 이름을 담고 무관한 이름은 담지 않는지 확인).

## BUG-18 — 컴파일 옵션을 고르는 동안 커서가 플로팅 창이 아닌 배경 패널에서 움직인다 · P1

**출처** 사용자 리포트: "컴파일 들어가서 컴파일 옵션 고를때 커서가 플로팅 창이 아닌 다른 창에서
움직이는 버그가 있어".

**재현** Deploy 뷰 → 모델 선택 → compile → 옵션 폼(플로팅)이 열린 상태에서 마우스 휠을 굴린다.
폼의 필드 커서는 그대로고, **배경 Model List 의 선택 바가 움직인다.**

**근본 원인 2개** (헤드리스 프레임 덤프로 확인)
1. **휠이 오버레이를 무시** — 마우스 분기가 항상 `app.move_sel()`(배경 리스트)을 호출했다.
   키보드에는 `Overlay::top()` 안전망이 있는데 휠에는 없었다(REG-01 과 같은 뿌리).
2. **화면에 커서가 2개** — 모달이 떠 있어도 배경 패널이 밝은 선택 바(`bg(C_HL())` + BOLD)를
   그대로 유지한다. 프레임 덤프에서 배경 5행의 하이라이트 바와 폼 9행의 `▶` 마커가 동시에 보이고,
   눈에 더 띄는 쪽은 배경의 solid 바다. 그래서 "커서가 다른 창에 있다"로 읽힌다.

**올바른 동작** 최상위 오버레이가 키보드를 소유하듯 **휠도 소유**한다. 배경 선택은 문맥으로 남기되
활성 커서로 보이지 않아야 한다.

**수정**
- `scroll_wheel(app, dir)` — 휠을 `Overlay::top()` 기준으로 라우팅: 옵션 폼(compile/prefetch/
  deploy/objective) → 필드 커서, place picker → 후보 커서, 액션 메뉴·팔레트 → 항목 커서,
  preview·logs → 스크롤(상한 클램프), 그 외 오버레이 → 무시, 오버레이 없으면 리스트.
  자유 입력(`e`) 중에는 휠 무반응 — 타이핑 중 대상 필드가 바뀌면 안 된다.
- `C_SEL_BG()` / `hl_style()` — 모달이 열린 프레임에서는 배경 선택 바를 `C_TRACK()`(dim)으로,
  BOLD 도 제거. 플래그는 `ui::draw` 가 프레임마다 `Overlay::top(app).is_some()` 로 설정.
  (thread-local: 렌더는 단일 스레드이고, 전역이면 병렬 렌더 테스트가 서로를 덮어썼다.)
- 회귀 테스트 2개: 휠이 폼 커서를 움직이고 `app.selected` 는 불변인지 / 모달 중 배경 선택 바가
  `C_TRACK()`, 모달 없을 때 `C_HL()` 인지.
